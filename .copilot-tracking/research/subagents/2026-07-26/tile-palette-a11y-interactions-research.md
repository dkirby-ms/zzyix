## Scope

* Topic: accessibility and interaction-state requirements for color swatches, material segmented control, and active summary in apps/client
* Target issue: #76
* Constraints: research-only, no source edits
* Questions investigated:
  * What a11y patterns are currently used in client UI components and tests
  * Which existing controls are closest to segmented controls and swatch options
  * How hover, focus, pressed, and selected states are represented in CSS and tests
  * Which test approaches best verify check indicator, accessible names, and fallback announcements

## Findings summary

* Current palette controls in apps/client/src/ui/ControlsPanel.tsx use semantic button elements with visible text for shape and material, and aria-label for color swatches.
* Selection for shape/material/swatch in controls is visual class-based active state, not explicit ARIA selected/pressed state.
* A segmented-control-like pattern already exists via Radix ToggleGroup in apps/client/src/ui/primitives/ToggleGroup.tsx with radio role semantics and data-state='on'.
* A second stateful-selection pattern exists via Radix Tabs in apps/client/src/ui/primitives/Tabs.tsx with tab/tablist semantics and data-state='active'.
* Live region and fallback announcement patterns already exist in lobby and loading/error surfaces:
  * aria-live='polite' in lobby panel and loading fallback
  * role='status' for loading indicator
  * role='alert' for hard failure fallback in CanvasErrorBoundary

## Evidence by requirement

### 1) Current a11y patterns in client UI tests/components

* ARIA labels
  * Palette container has an accessible landmark label: apps/client/src/ui/ControlsPanel.tsx
  * Swatches use explicit accessible names from color token: aria-label={`color ${swatch}`} in apps/client/src/ui/ControlsPanel.tsx
  * Collaborator summary has aria-label='Active collaborators' in apps/client/src/App.tsx
  * Tooltip trigger for connection errors has aria-label='View connection error details' in apps/client/src/ui/StatusIndicator.tsx

* Selected state semantics
  * Lobby canvas preset buttons expose pressed state through aria-pressed={isSelected}: apps/client/src/ui/LobbyScreen.tsx
  * Palette shape/material/swatch selected state uses className active only, without aria-pressed/aria-selected: apps/client/src/ui/ControlsPanel.tsx
  * Primitive ToggleGroup selected state uses Radix state attribute data-state='on': apps/client/src/ui/primitives/ToggleGroup.css
  * Primitive Tabs selected state uses data-state='active': apps/client/src/ui/primitives/Tabs.css

* Keyboard focus
  * Global focus ring baseline is defined using :focus-visible in apps/client/src/styles/base.css
  * Additional per-control focus-visible styles exist for buttons/swatches in apps/client/src/App.css and for primitives in:
    * apps/client/src/ui/primitives/ToggleGroup.css
    * apps/client/src/ui/primitives/Tabs.css
    * apps/client/src/ui/primitives/Dialog.css
    * apps/client/src/ui/StatusIndicator.css

* Live region announcements
  * Lobby container announces updates politely with aria-live='polite': apps/client/src/ui/LobbyScreen.tsx
  * Canvas loading fallback uses role='status' and aria-live='polite': apps/client/src/ui/CanvasLoadingFallback.tsx
  * Canvas hard-failure fallback uses role='alert': apps/client/src/App.tsx (CanvasErrorBoundary render branch)

* Existing a11y-oriented tests
  * Loading fallback test verifies status role and aria-hidden spinner:
    * apps/client/src/ui/CanvasLoadingFallback.test.tsx
  * Status indicator test verifies keyboard-focus discoverability of error details via accessible trigger name:
    * apps/client/src/ui/StatusIndicator.test.tsx
  * Primitive tests verify semantic roles generated by Radix wrappers:
    * ToggleGroup role='radio': apps/client/src/ui/primitives/ToggleGroup.test.tsx
    * Tabs tablist/tab/tabpanel roles: apps/client/src/ui/primitives/Tabs.test.tsx

### 3) How hover/focus/pressed/selected states are represented in CSS and tests

* Hover
  * Generic button hover lift effect via transform: translateY(-1px): apps/client/src/App.css (button:hover)

* Focus
  * Global :focus-visible ring variables: apps/client/src/styles/base.css
  * Specific selectors repeat focus-visible for key controls:
    * button:focus-visible, .swatch:focus-visible in apps/client/src/App.css
    * .ui-toggle-group-item:focus-visible in apps/client/src/ui/primitives/ToggleGroup.css
    * .ui-tabs-trigger:focus-visible in apps/client/src/ui/primitives/Tabs.css

* Pressed
  * Explicit ARIA pressed is currently present for lobby presets only (aria-pressed): apps/client/src/ui/LobbyScreen.tsx
  * No pressed-state ARIA in current shape/material palette controls: apps/client/src/ui/ControlsPanel.tsx

* Selected
  * Palette controls selected state:
    * className active for shape/material buttons
    * className 'swatch active' for selected color
    * files: apps/client/src/ui/ControlsPanel.tsx, apps/client/src/App.css
  * Primitive selected state:
    * data-state='on' for ToggleGroup
    * data-state='active' for Tabs
    * files: apps/client/src/ui/primitives/ToggleGroup.css, apps/client/src/ui/primitives/Tabs.css

* Test coverage shape today
  * Strong role/name assertions at integration layer in App tests for major regions and controls: apps/client/src/App.test.tsx
  * Primitive tests currently check role/class presence, not full keyboard interaction matrix:
    * apps/client/src/ui/primitives/ToggleGroup.test.tsx
    * apps/client/src/ui/primitives/Tabs.test.tsx
  * No dedicated tests currently target ControlsPanel swatch selected semantics or focus/press behavior

### 4) Recommended test approaches for issue #76 acceptance criteria

* Check indicator verification (for selected swatch/material)
  * Prefer semantic-first assertions where possible:
    * If implementation uses ToggleGroup/radio semantics, assert selected option with toHaveAttribute('aria-checked', 'true') or checked role semantics depending on rendered output.
    * If implementation keeps button semantics, assert aria-pressed='true' on the active choice.
  * Pair semantic assertion with visual cue guard:
    * Assert selected control includes active class or data-state selector token.
    * Avoid brittle pixel/computed-style checks unless required for regression confidence.

* Accessible names verification
  * Use getByRole with name for all interactive options.
  * For swatches, assert each option exposes stable user-facing name, not only raw hex token when product copy expects color names.
  * Keep names explicit in tests:
    * Example strategy: getByRole('button', { name: /color/i }) for swatches
    * Example strategy: getByRole('radio', { name: /ceramic/i }) if segmented/radio semantics are adopted

* Explicit fallback announcement verification
  * Loading fallback:
    * Assert role='status' and aria-live='polite' for non-blocking updates
    * Reuse and extend CanvasLoadingFallback test approach in apps/client/src/ui/CanvasLoadingFallback.test.tsx
  * Error fallback:
    * Assert role='alert' appears with user-visible recovery action (Retry)
    * Validate message content remains meaningful under lazy-load failure
  * Optional integration test:
    * Force CanvasErrorBoundary fallback path and assert alert + retry affordance are present

* Keyboard interaction and focus verification
  * Use @testing-library/user-event for tab/arrow/enter interactions instead of only fireEvent.
  * For segmented/radio controls, verify:
    * Tab reaches the group
    * Arrow keys move active option (if adopting roving tabindex via Radix)
    * Enter/Space confirms selection
  * Verify focus-visible readiness indirectly with behavior/state assertions plus one class-level check if needed.

* State transition matrix for acceptance
  * Add table-driven tests that exercise default, hover surrogate, focus, pressed/selected transitions where programmatically testable
  * Validate model-to-UI sync:
    * Clicking selected option maintains stable selected state
    * Changing palette can update active color deterministically (existing behavior already sets first palette swatch in App.tsx)

## Reusable patterns to apply

* Prefer existing primitive wrappers for robust semantics:
  * ToggleGroup for segmented single-select behavior with radio semantics
  * Tabs only when content panel semantics are truly needed
* Keep explicit accessible names on icon-only or color-only controls, following swatch aria-label precedent
* Keep focus style consistency by reusing global focus variables and :focus-visible tokens
* Distinguish announcement urgency:
  * role='status' with aria-live='polite' for progress/loading
  * role='alert' for failures requiring immediate attention
* For invisible supporting text, reuse VisuallyHidden primitive:
  * apps/client/src/ui/primitives/VisuallyHidden.tsx

## Gaps and risks relevant to issue #76

* ControlsPanel selected state is currently visual only for shape/material/swatch; this risks weaker SR discoverability for active option state.
* ControlsPanel currently lacks dedicated tests that validate selected semantics and keyboard behavior for swatches/material options.
* Primitive tests validate basic role rendering, but do not yet cover full interaction semantics such as arrow-key navigation in toggle groups.

## Recommended verification strategy

* Unit and component tests
  * Add focused tests around palette controls for:
    * accessible names
    * selected/pressed semantics
    * keyboard navigation and activation
    * check indicator presence for selected option
* Integration tests
  * Extend App-level tests to cover active summary and fallback announcements after state changes and error paths
* CSS-state coverage
  * Assert deterministic class/data-state markers rather than visual snapshots for selected/focus/pressed states
* Regression guardrails
  * Keep role-based queries as primary selectors
  * Avoid test ids for behavior that can be discovered through accessible roles/names

## Clarifying questions

* Should selected material/swatch controls be modeled as pressed buttons (aria-pressed) or radios within a radiogroup for final UX semantics?
* Should swatch accessible names remain hex-derived (for example, color #c96f3f) or move to human-friendly token names aligned to palette naming?
* Should the active summary expose a dedicated live region for state changes, or remain visually updated without explicit announcements unless error/loading states occur?

## Suggested next research

* Validate desired keyboard behavior contract from issue #76 design notes (arrow-key roving vs tab-only)
* Confirm acceptance wording for check indicator behavior under high-contrast and reduced-motion settings
