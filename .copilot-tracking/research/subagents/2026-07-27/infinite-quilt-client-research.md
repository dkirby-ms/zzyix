# Infinite Quilt Client Research

## Research Scope

Research GitHub issue 53 client-side implications for replacing discrete canvases with a very large finite wraparound canvas made of adjacent, potentially differently owned patches. Product code is out of scope.

Questions:

* Where are canvas dimensions, coordinate systems, grid and tile types, interactions, rendering, identity, subscriptions, state assumptions, tests, and scripts defined?
* Which existing constraints determine the adaptation boundary?
* Which client architecture best supports finite toroidal wrapping, patch ownership, viewport virtualization, cross-boundary editing, and current rendering technology?

## Initial Hypothesis

The client already streams world chunks from the current viewport, so the smallest viable architecture should preserve Three.js rendering and viewport chunk subscriptions while adding a toroidal global-coordinate and patch-resolution layer. This hypothesis is false if chunk subscriptions are not viewport-derived or are inseparable from one discrete session identity.

## Findings

### Issue Scope and Repository Guidance

GitHub issue 53, `[Feature] "Infinite" scrolling canvas`, asks for an extremely large canvas that wraps from one end to the other. The issue body does not define patch ownership, topology dimensions, editing permissions, migration, or seam behavior. The adjacent, differently owned patch model in this research request is therefore an additional design requirement that needs a product and protocol contract before implementation.

No `.github/copilot-instructions.md` exists in this workspace. The report follows the applicable HVE Core Markdown and writing guidance. The required leading `<!-- markdownlint-disable-file -->` exempts this research artifact from the general frontmatter requirement.

### Current Client Architecture

#### Canvas dimensions and selectors

* The shared contract defines the default bounded world as `[-5.2, 5.2] x [-3.4, 3.4]`, or 10.4 x 6.8 world units, and a runtime chunk size of 8 world units. See `apps/server/src/contracts.ts:29-64`.
* Canvas presets are `classic`, `expanded`, and `vast`. The server multiplies both dimensions and bounds by 1, 2, or 3, yielding the client labels 10.4 x 6.8, 20.8 x 13.6, and 31.2 x 20.4. See `apps/server/src/contracts.ts:152-179`, `apps/server/src/index.ts:101-107`, `apps/server/src/index.ts:687-706`, and `apps/client/src/ui/LobbyScreen.tsx:18-31`.
* The client defaults new sessions to `expanded`, sends the selected preset during creation, and replaces its world bounds from the session snapshot. See `apps/client/src/App.tsx:350-357`, `apps/client/src/App.tsx:498-511`, and `apps/client/src/App.tsx:519-536`.
* The relevant DOM layout selectors are `.canvas-workspace`, a canvas plus 280 px tool column, and `.canvas-shell`, the clipped relative container with at least 60 dynamic viewport-height units. The actual WebGL element is forced to fill that shell. See `apps/client/src/App.css:218-225` and `apps/client/src/App.css:481-493`.
* The canvas is not an HTML drawing canvas managed directly by application code. `MosaicScene` mounts one React Three Fiber `<Canvas>` with an orthographic Three.js camera. See `apps/client/src/render/MosaicScene.tsx:1-16` and `apps/client/src/render/MosaicScene.tsx:526-603`.

#### Coordinates, grid cells, and tile domain types

* Client world coordinates are plain JavaScript `{ x: number, y: number }` vectors. A chunk ID is the string `${number}:${number}`. See `apps/client/src/domain/math2d.ts:1-8`.
* Chunk coordinates use `Math.floor(world / chunkSize)`, including for negatives. Visible chunk IDs are generated by scanning the viewport's rectangular chunk range from minimum X and Y to maximum X and Y. See `apps/client/src/domain/math2d.ts:59-87`.
* Tile transforms contain an absolute world position, rotation, and optional mirror flag. There is no patch address, local coordinate, canonical world period, or display image offset. See `apps/client/src/domain/tileGeometry.ts:7-17` and `apps/client/src/domain/placementSolver.ts:21-31`.
* Grid cells are unbounded integer lattice coordinates. Slot IDs embed the pattern, global cell X and Y, and template slot. Grid transforms are derived directly in world coordinates from basis vectors. See `apps/client/src/domain/gridPatterns.ts:20-49` and `apps/client/src/domain/gridPatterns.ts:179-221`.
* Grid viewport generation is already virtualized: the visible camera rectangle is converted to a lattice cell range with overscan, and only those slots become line segments. See `apps/client/src/domain/gridPatterns.ts:150-177`, `apps/client/src/render/GridOverlay.tsx:47-95`, and `apps/client/src/render/gridOverlayGeometry.ts:62-86`.
* Placement and collision are Euclidean. The client transforms candidate and settled polygons into the same absolute plane, performs SAT overlap tests, enforces bounded edges, and checks adjacency by minimum outline distance. See `apps/client/src/domain/placementSolver.ts:67-133` and `apps/client/src/domain/placementSolver.ts:152-261`.

#### Pan, zoom, pointer, and hit testing

* `App` owns `cameraPan` and a fixed policy of min zoom 20, max zoom 140, and pan sensitivity 0.02. See `apps/client/src/App.tsx:338-343`.
* Wheel zoom is delegated to `OrbitControls`. Its rotation and built-in panning are disabled. Middle-button drag is handled on a transparent interaction plane and converted from screen-pixel deltas to `cameraPan`; right-button drag rotates the active tile. See `apps/client/src/render/MosaicScene.tsx:214-313` and `apps/client/src/render/MosaicScene.tsx:500-518`.
* `cameraPan` is used as the OrbitControls target, but the viewport reporter reads the orthographic camera's actual position each frame. See `apps/client/src/render/MosaicScene.tsx:333-377` and `apps/client/src/render/MosaicScene.tsx:500-518`.
* Pointer world positions come from React Three Fiber's plane intersection (`event.point`). The plane is centered on and sized from bounded world dimensions plus six units. A very large literal plane is therefore the current pointer surface. See `apps/client/src/render/MosaicScene.tsx:225-306`.
* Hover selection is application-level point-in-polygon testing over the entire tile array in reverse order. It is $O(n)$ per pointer update and has no spatial index or periodic nearest-image logic. See `apps/client/src/App.tsx:263-299` and `apps/client/src/App.tsx:1120-1148`.
* Pointer and selection presence are throttled. They transmit one absolute position or one tile ID under the current canvas ID. See `apps/client/src/App.tsx:650-780`.

#### Rendering, culling, and precision

* Every retained tile renders as its own Three.js group and mesh. Geometry is cached by shape, but every tile creates its own material hook result and registers a `useFrame` settle-animation callback. See `apps/client/src/render/MosaicScene.tsx:18-21`, `apps/client/src/render/MosaicScene.tsx:98-153`, and `apps/client/src/render/materials.ts:44-70`.
* `MosaicScene` maps the complete `tiles` prop without explicit viewport filtering, instancing, batching, or level-of-detail substitution. Three.js frustum culling can avoid drawing off-screen meshes, but React objects, materials, callbacks, and tile state remain allocated. See `apps/client/src/render/MosaicScene.tsx:380-461`.
* Chunk snapshots replace tiles in an incoming fine chunk, but unsubscribing does not evict tiles from `SequencedTilesState.tiles`. The client therefore has network subscription limiting, not full state or render virtualization. See `apps/client/src/App.tsx:566-585` and `apps/client/src/App.tsx:826-952`.
* Aggregate snapshots retain existing fine tiles and discard aggregate counts after advancing revision metadata. There is no aggregate visual representation at low zoom. See `apps/client/src/App.tsx:566-585` and `apps/client/src/App.test.tsx:547-652`.
* The background, interaction plane, and visible canvas bounds allocate geometry proportional to the complete world bounds. See `apps/client/src/render/MosaicScene.tsx:293-331` and `apps/client/src/render/MosaicScene.tsx:462-483`.
* JavaScript numbers can safely represent very large logical patch indices within a defined finite topology, but WebGL vertex transforms use floating-point GPU coordinates. Sending very large absolute positions to the scene will eventually cause jitter, unstable hit testing, and visible gaps. Rendering should use camera-relative local positions near the origin even if navigation retains an unwrapped logical coordinate.

#### Routing and current canvas identity

* There is no client router. `main.tsx` renders `App` directly, while `App` switches a local `mode` between `lobby` and `canvas`. See `apps/client/src/main.tsx:1-10` and `apps/client/src/App.tsx:344-352`.
* The selected session ID is persisted in `sessionStorage`, but startup always returns to the lobby and only marks the stored ID as the previous session. Joining or creating sets one current `sessionId`. See `apps/client/src/network/session.ts:4-6`, `apps/client/src/network/session.ts:47-57`, and `apps/client/src/App.tsx:464-511`.
* Lobby concepts and labels assume a list of independent canvases, each with one size and participant count. See `apps/client/src/ui/LobbyScreen.tsx:58-117`.
* A quilt model needs a new stable route/identity distinction: quilt/world identity, canonical patch identity, viewport location, and possibly owner identity. Reusing `sessionId` for all four would preserve the current ambiguity and prevent durable deep links.

#### WebSocket subscriptions and state assumptions

* One Socket.IO connection authenticates with exactly one `sessionId` and `clientId`; changing the session tears down and recreates the connection. See `apps/client/src/network/useSocketConnection.ts:23-55` and `apps/client/src/network/useSocketConnection.ts:108-147`.
* The shared protocol joins a session room and scopes whole-session tile, presence, pointer, and selection broadcasts to that room. See `apps/server/src/contracts.ts:201-210`.
* `App` stores one flat `SequencedTilesState` with one global `lastOpSeq`, one revision, and one `requiresSnapshot` flag. See `apps/client/src/interaction/controller.ts:24-29` and `apps/client/src/interaction/controller.ts:66-76`.
* Chunk requests include the same current `canvasId`; chunk IDs are only coordinates inside that canvas. Snapshot and mutation payloads also carry a single canvas-level sequence and revision. See `apps/server/src/contracts.ts:349-415`.
* Viewport changes are hysteresis-gated, expanded by one chunk, and capped at 64 subscriptions (128 hard cap before the soft cap is applied). See `apps/client/src/App.tsx:84-92` and `apps/client/src/App.tsx:826-909`.
* The chunk list is not ordered by distance to viewport center. Applying the budget can retain a lower-left scan prefix and omit closer chunks. See `apps/client/src/domain/math2d.ts:67-87` and `apps/client/src/domain/math2d.ts:108-121`.
* Chunk events are reconciled through whole-session contiguous operation sequencing. A client subscribed to only some chunks can observe gaps caused by operations elsewhere, so this state model does not naturally support patch-scoped ownership or independently revisioned visible regions. See `apps/client/src/interaction/controller.ts:107-153` and `apps/client/src/App.tsx:587-648`.
* Initial and recovery snapshots still contain `session.tiles`, and `onSnapshot` replaces the client state with that whole array. A huge quilt cannot preserve this fallback without defeating virtualization. See `apps/server/src/contracts.ts:317-324` and `apps/client/src/App.tsx:519-536`.

### Concrete Adaptation Boundaries

The smallest coherent client change is not a modification to `MosaicScene` alone. It crosses these ownership boundaries:

1. Add a pure topology/resolver domain module near `apps/client/src/domain/math2d.ts`. It should own positive modulo, canonical patch addressing, patch-local normalization, nearest periodic image, viewport-to-patch intersections, and camera-relative display offsets.
2. Replace the flat `SequencedTilesState.tiles` and single revision assumptions in `apps/client/src/interaction/controller.ts` with patch/chunk keyed state, independent cursors, and explicit eviction. Keep optimistic mutations keyed by stable tile ID and target patch.
3. Refactor `apps/client/src/App.tsx` from session orchestration into quilt viewport orchestration. It must resolve visible canonical patches, subscribe/unsubscribe by patch/chunk, map pointer display positions to canonical positions, and keep presence image-aware.
4. Evolve `apps/client/src/network/useSocketConnection.ts`, `apps/client/src/network/session.ts`, and the shared contracts so a connection joins one quilt while subscribing to many patch/chunk streams. Patch ownership and authorization outcomes must be exposed to the client.
5. Keep `apps/client/src/render/MosaicScene.tsx` and React Three Fiber, but pass only visible display instances. Introduce render-image identity separate from authoritative tile identity, camera-relative coordinates, seam duplicates, and eventually instancing or batching by shape/material.
6. Make `apps/client/src/domain/placementSolver.ts`, `apps/client/src/domain/gridPlacement.ts`, `apps/client/src/domain/gridPatterns.ts`, and `apps/client/src/render/gridOverlayGeometry.ts` topology-aware through resolved local neighborhoods. Do not spread `% worldWidth` expressions through these modules.
7. Replace the lobby's independent-canvas preset workflow in `apps/client/src/ui/LobbyScreen.tsx` with world entry, patch navigation/claiming, or another product-approved model. Add URL routing if locations must be shareable and reload-stable.

### Important Constraints

* The largest current patch is 31.2 x 20.4 world units, but the runtime chunk size is 8. Patch dimensions are not integer multiples of chunks. The new design must either align patch size to chunk boundaries, define chunks patch-locally, or support chunks split by patch boundaries. Silent reuse of both values produces ambiguous ownership at edges.
* A tile polygon can cross a patch boundary. The model must decide whether ownership is determined by anchor point, all intersected patches, or a prohibition/margin. The current transform has one position and no footprint ownership metadata.
* A torus removes outer canvas rejection but not patch authorization. Client confidence should distinguish geometric invalidity from a server-authoritative read-only or forbidden patch.
* Rendering a seam needs duplicate display images, not duplicate authoritative tiles. Keys should include tile ID and periodic image offset; selection, mutation, undo, and presence must collapse back to one canonical identity.
* The viewport can cross the same canonical patch more than once only if the viewport becomes comparable to the world period. Either cap zoom-out so the viewport is smaller than each period or deduplicate canonical subscriptions while permitting multiple display images.
* The current `cameraPan` can grow indefinitely. Keep an unwrapped navigation coordinate for smooth directional panning, but periodically rebase the Three.js camera and scene around zero. Canonicalization should happen at resolver and protocol boundaries, not every frame of navigation.
* Grid patterns are anchored at world origin. The product must choose a quilt-global lattice, a patch-local lattice that may break at patch edges, or per-patch pattern metadata. A quilt-global lattice gives continuous seams only when world periods are compatible with each pattern basis.
* Undo currently means the last retained tile placed by this client. Eviction makes that incorrect. Undo history must become explicit operation metadata rather than a reverse scan of visible tiles. See `apps/client/src/App.tsx:990-1040` and `apps/client/src/App.tsx:1308-1321`.
* Status counts currently display `sequencedState.tiles.length`, which will become a visible-cache count after proper eviction, not the quilt's total tile count. See `apps/client/src/App.tsx:1341-1350`.

## Architecture Options

### One Huge Global Coordinate Plane

Store every tile at a canonical global X/Y and wrap with positive modulo at world limits.

Advantages:

* Minimal apparent change to existing transforms and grid math
* Straightforward server query by global chunk
* Quilt-global grid patterns remain conceptually simple

Disadvantages:

* Patch ownership needs repeated coordinate-to-patch derivation and is easier to bypass accidentally
* Large GPU coordinates need a separate render-origin system anyway
* Seam collision, hit testing, and duplication still require nearest-image resolution
* Migration and patch-local exports are less explicit

This is acceptable only if global coordinates are a logical API and never passed directly to GPU rendering at large magnitudes.

### Canonical Patch-Local Storage With a Resolver

Store authoritative positions as `(patchX, patchY, localX, localY)`, with finite patch counts and positive modulo on patch indices. Maintain an unwrapped navigation coordinate for camera continuity. A resolver maps canonical positions to the nearest display image around the viewport.

Advantages:

* Ownership, permissions, revision cursors, caching, migration, and subscription keys share the same explicit boundary
* Local coordinates stay near zero for geometry and persistence
* Visible state can be fetched, evicted, retried, and reconciled per patch/chunk
* Existing canvas data can migrate naturally into one patch without changing tile-local geometry

Disadvantages:

* Every pointer, placement, hit-test, grid, presence, and render path must use the resolver consistently
* Cross-patch polygons require a documented anchor/authorization rule
* Quilt-global grid slot identity requires a canonical global cell address or topology-compatible periods

This is the preferred representation.

### Independent Canvas Scenes Stitched in the UI

Keep each current session/canvas intact and mount adjacent scenes or canvases.

Advantages:

* Superficially preserves current ownership and session storage
* Patches can load independently

Disadvantages:

* Multiple WebGL canvases duplicate contexts, cameras, controls, lights, and event routing
* Cross-patch tiles, hit testing, selections, shadows, and smooth zoom become brittle
* Current Socket.IO hook still models one session per connection
* DOM or multiple-canvas seams would be visible and hard to make topologically correct

This option should be rejected.

### Renderer Choice

* DOM tiles are not applicable. Current tiles are extruded Three.js geometry with physical materials, lighting, fog, and animated transforms.
* Canvas 2D would require replacing the established visual and interaction stack and would not solve state virtualization or toroidal identity.
* One React Three Fiber/WebGL scene remains appropriate. The adaptation should improve its data feed and batching rather than replace it.

## Preferred Approach

Use canonical patch-local authoritative coordinates with a pure toroidal resolver, one quilt-level Socket.IO connection, patch/chunk scoped subscriptions and cursors, and one camera-relative React Three Fiber scene.

Recommended model:

```text
QuiltTopology = {
	patchColumns,
	patchRows,
	patchWidth,
	patchHeight
}

CanonicalPosition = {
	patch: { x, y },
	local: { x, y }
}

NavigationPosition = unwrapped logical X/Y
DisplayInstance = authoritative tile + periodic image offset - render origin
```

The resolver should provide these invariants:

* `canonicalize(unwrapped)` always returns patch indices in finite ranges and local coordinates in a single half-open interval
* `toUnwrappedNear(canonical, reference)` returns the nearest periodic image to the camera or pointer reference
* `visiblePatchImages(viewport)` returns canonical patch IDs plus unwrapped image offsets, deduplicating subscriptions but not render images
* `minimumImageDelta(a, b)` drives seam-aware collision, adjacency, snapping, cursor interpolation, and hit testing
* Canonical IDs never include display offsets

Rendering sequence:

1. Keep camera navigation unwrapped for smooth panning.
2. Rebase the Three.js render origin near the camera before coordinates become large.
3. Resolve visible periodic patch images for the camera rectangle plus overscan.
4. Subscribe once per canonical patch/chunk and retain a bounded cache.
5. Produce display instances only for visible images; duplicate tiles into neighboring periodic images when their bounds or the viewport cross a world seam.
6. Render static settled tiles in instances or merged batches grouped by shape and material/color strategy. Keep ghost, settling tiles, cursors, and selection halos as small dynamic objects.

Interaction sequence:

1. Intersect pointer events with a camera-local plane rather than a world-sized finite plane.
2. Convert the display hit to an unwrapped navigation point.
3. Canonicalize to patch and local coordinates for placement and network payloads.
4. Gather candidate tiles from the target patch and its periodic/adjacent neighborhood.
5. Transform candidates to their nearest images and run the existing Euclidean SAT logic locally.
6. Return authoritative tile IDs from hover and selection even when the hit display object is a seam duplicate.

Selection and copy/paste:

* The current client has remote single-tile selection presence but no local multi-selection, copy, paste, or clipboard implementation. See `apps/client/src/App.tsx:700-780` and the absence of clipboard code under `apps/client/src`.
* Future selection state should store canonical tile IDs plus an unwrapped selection anchor. A drag rectangle crossing a seam must test periodic images and deduplicate by tile ID.
* Copy should serialize geometry relative to the unwrapped anchor, not raw canonical coordinates. Paste should canonicalize each translated tile independently, group mutations by target patch, and request authorization atomically or return clear partial-failure semantics.
* Tiles copied across the world period need one logical occurrence in clipboard data even if multiple images are visible.

Why this approach fits the repository:

* It retains React Three Fiber, the existing tile geometry, material vocabulary, orthographic interactions, and most local Euclidean geometry code.
* It aligns the new ownership requirement with cache and synchronization boundaries instead of deriving ownership ad hoc from huge coordinates.
* It supports a bounded state footprint and camera-relative GPU precision.
* It gives existing canvases a direct migration target as individual patches.

## Test Strategy

### Existing Coverage to Preserve

* App tests cover lobby transitions, snapshot bounds, pointer validity, chunk snapshot modes, chunk resync requests, capability gating, pan/zoom wiring, optimistic placement, collaboration, and responsive overflow. See `apps/client/src/App.test.tsx:143-810` and `apps/client/src/App.test.tsx:883-1458`.
* Domain tests cover bounded/unbounded placement, overlap, grid slot determinism, negative lattice coordinates, viewport overscan, and valid fill sequences. See `apps/client/src/domain/placementSolver.test.ts:9-94`, `apps/client/src/domain/gridPlacement.test.ts:10-88`, and `apps/client/src/domain/gridPatterns.test.ts:15-91`.
* Scene tests cover right-drag rotation and middle-drag panning. See `apps/client/src/render/MosaicScene.test.tsx:22-104`.
* Playwright multi-user tests cover exact-once convergence and stale/out-of-order revisions, but all users join one session and use small absolute coordinates. See `e2e/support/multiUser.ts:224-369` and `e2e/multi-user-fixtures.spec.ts:53-317`.

### Required New Tests

1. Pure topology property tests for positive modulo, half-open edge normalization, round trips, negative navigation, multiple full periods, nearest-image deltas, and corner wrapping.
2. Viewport resolver tests for left/right, top/bottom, and four-corner seams; canonical subscription deduplication; image duplication; center-distance ordering; zoomed-out repeated images; and bounded cache size.
3. Placement tests for overlap, grout adjacency, and grid snapping across each seam and corner, including one authoritative tile rendered twice.
4. Hit tests proving that seam duplicates select and mutate the same tile ID and that remote cursor/selection positions choose the nearest visible image.
5. State tests for patch-scoped snapshots, independent cursors, stale patch updates, unsubscribe eviction, optimistic moves across patch boundaries, reconnect recovery without a whole-quilt snapshot, and authorization rejection.
6. Render tests or instrumentation with explicit limits for retained tile records, React objects, `useFrame` subscribers, draw calls, and frame time while traversing many patches.
7. E2E tests with users in adjacent differently owned patches, concurrent edits near a seam, wraparound presence, read-only neighbors, reconnection while straddling a seam, and exact-once canonical tile identity.
8. Copy/paste tests only after product semantics are defined: seam-crossing selection deduplication, relative offsets, multi-patch authorization, and atomicity.

## Unresolved Questions

* What are the exact finite patch columns, rows, and dimensions? Must dimensions remain one of the current presets?
* Does each current canvas become one patch, and can patches have different dimensions or grid patterns?
* Is ownership assigned to the tile anchor patch, every intersected patch, or are cross-patch tiles forbidden?
* Can users edit unowned or neighboring patches, claim patches, transfer ownership, or collaborate through ACLs?
* Is the quilt global, tenant-scoped, or composed of multiple named worlds? This determines route and Socket.IO identity.
* Should users be allowed to zoom out far enough to see the same canonical patch more than once?
* Is the grid lattice global and seamless, or can each patch choose a pattern/origin? Current world periods are not guaranteed to align with all pattern bases.
* Must paste across patches be atomic? How should partial authorization failures appear?
* What does the status tile count represent after virtualization: visible cache, current patch, owned patches, or global aggregate?
* How should collaborator rosters scope presence: entire quilt, visible patches, owned patches, or an interaction radius?
* Does selecting or linking to a location require a stable URL and reload restoration?

## Recommended Next Research

* Define topology, ownership, ACL, cross-boundary tile, and migration semantics with product and server owners
* Prototype the pure toroidal resolver and property tests before changing rendering or networking
* Measure tile density, visible tile counts, draw calls, material count, and frame time on the current `vast` canvas to set virtualization budgets
* Align patch dimensions with chunk partitioning or specify the intentional mismatch
* Design patch-scoped protocol cursors and reconnect behavior so the client never requires a whole-quilt snapshot
* Validate Three.js instancing/material tradeoffs against the existing per-tile colors, physical variants, settle animation, and selection halos
